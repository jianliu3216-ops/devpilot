# CICD 智能流水线开发流程

本项目是一套基于 Claude Code 的 AI 辅助开发智能流水线，实现从简单自然语言需求 → 需求分析 → PRD → 软件设计 → 代码实现 → 测试用例 → 测试报告的全流程自动化。每个阶段产出需要人工确认后才进入下一阶段，确保质量可控。

---

## 设计思路

当前目录 `本仓库根目录（claude-code-cicd）` 是**共用框架目录**，只存放：
- 所有 Agent 定义（`.claude/agents/`）
- 所有钩子脚本（`.claude/hooks/`）
- 框架核心代码（`.claude-collective/`）
- 全局行为规则（`CLAUDE.md`）
- 使用说明（`README.md` 本文件）

**当你要分析某个项目 / 开发某个功能时**：
- 你提供目标项目目录路径（比如 `D:\projects\my-existing-project`）
- 所有生成的产出文档（私域知识库、需求分析、PRD、设计、测试用例、测试报告）都**输出到目标项目目录下**
- 不会污染当前共用框架目录，避免文件冲突
- 每个项目自己保管自己的文档，清晰分离

### 测试代码目录规则

- **位置**：`[目标项目]/tests/{需求标识}/`，与 `docs/` 同级
- **不放在源码子目录里**：避免测试代码散落在深层业务目录中，保持项目根目录结构清晰
- **按需求隔离**：每个需求的测试代码独立目录，互不干扰
- **目录确认机制**：生成测试代码前，AI 必须先输出目录路径供用户确认，支持自定义调整

**目录确认流程（任务6/任务8 生成测试代码时）：**
```
AI: 📂 测试代码目录确认
    默认路径：D:\projects\my-app\tests\user-login\
    包含文件：
      - run_tests.js          （测试运行脚本）
      - test_user_login.lua   （功能测试脚本）

    是否需要调整路径？（直接回车确认，或输入自定义路径）

用户: 直接回车 → 用默认路径
用户: 改到 D:\my-tests\user-login\ → 用自定义路径
```

### 需求标识规则

每个需求有一个**英文短标识**（kebab-case），用于创建独立的文档目录。用户只需输入中文需求描述，AI 自动建议英文标识，**必须提示用户确认后才能继续**：

```
用户: 开始任务3，需求：用户登录注册模块，目标项目：D:\projects\my-app

AI: 需求【用户登录注册模块】英文标识建议：user-login
    是否需要调整？（确认后将以 docs/user-login/ 作为文档目录）

用户: 没问题 → 用 user-login
用户: 改成 login-register → 用 login-register
```

> 关键点：
> - 框架目录和项目产出**完全分离**，不会互相干扰
> - 不同需求之间**完全隔离**，互不覆盖
> - knowledge-base 保持共享（整个项目一份），变更时增量更新
> - 测试代码放在 `tests/{需求标识}/`（与 docs 同级），不放在源码子目录里
> - 生成测试代码前**必须确认目录路径**，防止放错位置

## 核心概念：/van 命令是什么？

`/van` 是 claude-code-collective 提供的**自动路由命令**。

**工作原理：**
```
你输入: /van "基于需求分析文档生成 PRD"
          ↓
task-orchestrator (路由 Agent) 分析你的请求
          ↓
自动识别需求 → 派给对应的专业 Agent
          ↓
专业 Agent 开始干活，输出结果
```

**你不需要记**哪个功能应该找哪个 Agent，只需要用 `/van "描述你要做什么"` 就可以了，路由自动完成。

### 任务 2：生成历史项目私域知识库 ⏳ 等待开始

- **作用**：当您已有历史项目需要接入 AI 辅助开发时，先生成项目私域知识库，让 AI 理解现有代码结构、编码风格、可复用资产。**所有后续阶段都会自动带上这个知识库作为参考**，保证新增代码的风格和结构与现有项目保持一致。**关键：后续 Agent 只需要参考这个知识库理解项目，不需要重新扫描读取整个项目代码**，节省上下文。
- **你的输入示例**：
  ```
  开始任务 2，目标项目路径：D:\projects\my-existing-project
  ```
- **工具**：直接调用您自定义的 Skill → `/project-knowledge-base`
- **实际调用示例（框架自动执行，你不需要输入）**：
  
  ```
  /project-knowledge-base --target "D:\projects\my-existing-project" --output "D:\projects\my-existing-project\docs\knowledge-base\PROJECT_KNOWLEDGE_BASE.md"
  ```

## 变更分级机制（全流程通用）

### 为什么需要分级？

不管是**新需求**还是**需求变更**，都存在变更规模差异：
- **小变更**：新增一个字段、改一个常量 → 走完整 6 阶段流程太重
- **中变更**：新增功能模块 → 标准流程正好
- **大变更**：框架升级涉及上百文件 → 逐文件写详细设计不现实，需要轻量流程

**分级不是任务9专属，而是全流程通用的自动适配机制**。从任务3（需求分析）开始评估，后续每个阶段自动适配。

### 三级变更定义

| 级别 | 名称 | 判定条件 | 典型场景 |
|------|------|----------|----------|
| **S** | 小变更 | 修改 ≤ 3 个文件，逻辑简单 | 新增字段、修改常量、调整日志格式 |
| **M** | 中变更 | 修改 4-15 个文件，或涉及 2-3 个模块 | 新增功能模块、调整判定逻辑、接口变更 |
| **L** | 大变更 | 修改 > 15 个文件，或跨模块/全局性变更 | 框架版本升级、批量依赖更新、全局重构 |

### 分级触发时机

| 触发点 | 场景 | 说明 |
|-------|------|------|
| **任务3（需求分析）** | 新需求 | AI 分析需求后自动评估级别，**首次分级，后续阶段继承** |
| **任务5（软件设计）** | 设计阶段发现影响范围扩大 | 如果设计时发现比预期更复杂，可升级级别 |
| **任务6（代码实现）** | 实现时发现超出预估 | 如果实现时发现文件数远超预期，可升级级别 |
| **任务9（需求变更）** | 变更需求 | AI 分析变更影响后自动评估级别 |

> **级别只能升级，不能降级**：如果任务3评估为 M 级，任务5发现实际是 L 级，会提示你确认升级。但不会从 M 降为 S。

### AI 自动分级规则

**核心规则：用户不指定级别时，AI 必须自动评估并停下来等用户确认，不能跳过分级直接进入后续阶段。**

AI 在首次分级点（任务3 或任务9.2）自动分析并输出分级结论：

```
📊 变更级别评估

变更描述：Spring Boot 从 2.7 升级到 3.2
预计影响文件数：约 80+ 文件（pom.xml、application.yml、import 语句、废弃 API 替换）
预计影响模块：全局（跨所有模块）
变更级别：L（大变更）

判定依据：
- 影响文件数 > 15 → L 级
- 涉及全局依赖变更 → L 级
- 无新增业务功能，纯技术升级

后续流程：轻量流程（L 级）
是否调整？（直接回车确认，或输入 S/M 修改级别）
```

**两种方式二选一：**

| 方式 | 说明 | 示例 |
|------|------|------|
| **不指定级别（默认）** | AI 自动评估 → 输出分级建议 → **必须等用户确认** → 再进入后续阶段 | `开始任务3，需求：升级Spring Boot` |
| **手动指定级别** | 用户直接指定，跳过自动评估，立即进入对应流程 | `开始任务3，级别：L，需求：升级Spring Boot` |

> ⚠️ **强制规则**：即使用户不指定级别，AI 也不能跳过分级提示直接按某个级别执行。必须先输出分级评估，等用户确认（或调整）后，才能进入下一阶段。

### 三级流程对照

| 阶段 | S 级（小变更） | M 级（中变更） | L 级（大变更） |
|------|:---:|:---:|:---:|
| 需求分析(任务3) | ✅ 简要需求分析 | ✅ 完整需求分析 | ✅ 完整需求分析 |
| PRD(任务4) | 不需要 | ✅ 完整 PRD | ✅ 完整 PRD |
| 软件/策略设计(任务5) | 不需要 | ✅ `03-software-design.md` | ⬇️ `03-change-strategy.md` |
| 代码实现(任务6) | ✅ 直接改代码 | ✅ TDD 流程 | ✅ 按策略分批执行 |
| 测试用例(任务7) | 跳过（自动化覆盖） | ✅ `04-test-cases.md` | ⬇️ `04-regression-checklist.md` |
| 测试报告(任务8) | ✅ 简要结果报告 | ✅ 完整测试报告 | ✅ 完整测试报告 |
| 知识库更新(任务8.5) | ✅ 增量更新 | ✅ 增量更新 | ✅ 增量更新 |

L 级变更多数是**技术性批量操作**（非新业务功能），不需要逐模块写详细设计，核心是**策略清晰 + 自动化验证**。

### 任务 9：需求变更

1. **你描述变更**：指定需求标识 + 变更内容，比如"执行任务9，需求标识：user-login，需求变更：登录页面增加忘记密码链接"
2. **AI 变更影响分析**：AI 自动分析，输出：
   - 变更影响了哪些模块
   - 需要重做的阶段 + 可以保留的阶段 + 理由
   - 在该需求的 `CHANGELOG.md` 中记录变更
3. **你确认变更范围**：确认 AI 分析是否正确，可以调整
4. **AI 增量重做**：只重做受影响的阶段，每个阶段完成后等你确认
5. **代码实现 + 测试**：遵循 TDD 原则
6. **测试报告**：生成测试报告
7. **知识库增量更新**：执行任务8.5
8. **你确认** → 变更流程结束

**核心优势：** 不需要从头走全量流程，只重做受影响的部分，节省资源，避免业务偏差。

## 知识库贯穿整个开发流程（强制规则）

> 🎯 **核心思想：知识库 = 单一事实源（Single Source of Truth）**
> 所有开发阶段都必须「先读知识库，再写知识库」，不能脱离知识库单独进行。PUML 流程图是知识库的核心组成，也是设计和测试阶段的强制参考依据。

---

### 规则 1：PUML 流程图的标准格式与变更记录

**所有 PUML 文件必须包含：**
```plantuml
@startuml
' 项目：{项目名称}
' 流程图类型：{主业务流程/协议处理/OTA升级等}
' 生成时间：{YYYY-MM-DD}
' 激活标签：{对应特征标签}
'
' 变更记录（倒序排列，最新在最上面）：
' v{版本号} - {日期} - {变更内容描述}
' v{版本号} - {日期} - {初始版本}
'
skinparam backgroundColor #FEFEFE
skinparam rectangle {
  BackgroundColor #E8F4FD
  BorderColor #2196F3
}
skinparam note {
  BackgroundColor #FFF9C4
  BorderColor #FBC02D
}

title {流程图标题}

' 图内容...
@enduml
```

**强制要求：**
- 不能缺失任何元数据头部
- 版本号必须和 BASE.md 版本号一致
- 每次修改流程图必须追加变更记录
- 所有流程图必须使用统一的 skinparam 样式

---

### 规则 2：需求变更阶段必须先读知识库

- **必须做**：读取相关模块的 DETAIL 文档 + 对应的 PUML 流程图，评估变更影响范围
- **必须做**：变更完成后，**增量更新**受影响的知识库章节，并在变更记录中追加条目
- **禁止**：不看已有实现就凭空设计变更方案

---

### 规则 3：需求分析 / PRD 阶段必须建立知识库锚点

- **必须做**：读取 BASE.md 整体架构 + 技术栈约束，确保需求不超出已有技术能力
- **必须做**：参考同领域已有 PUML 流程图，复用已验证的实现模式
- **必须做**：在 PRD 中增加「知识库锚点」章节，标明：
  ```markdown
  ## 知识库锚点
  - 关联知识库版本：PROJECT_KNOWLEDGE_BASE.md @ v2.1
  - 关联模块域：加密模块域、升级模块域
  - 关联流程图：ota_flow.puml、security_flow.puml
  - 预计变更：将修改 ota_flow.puml 第 3-5 节点，新增降级流程
  ```
- **必须做**：新增需求涉及新流程的，在 PRD 中附带 PUML 流程图草稿

---

### 规则 4：软件设计阶段强制引用 PUML 流程图（必须校验）

✅ **必须引用已有 PUML 流程图作为基准**，不能脱离已实现的代码架构  
✅ 修改流程的，必须在设计文档中标注「此设计修改了 `{文件名}.puml` 中第 X 节点」  
✅ 新增流程的，设计评审通过后必须生成新的 `*.puml` 文件并入知识库  

❌ **禁止**：设计和已实现代码完全脱节，出现「设计一套、实现另一套」  
❌ **禁止**：只写设计文档不更新知识库，导致设计和实现两张皮  

---

### 规则 5：所有开发文档必须包含「知识库锚点」

需求分析文档、PRD、设计文档、测试报告，**每个文档顶部必须包含知识库锚点**，格式见规则 3。

---

### 规则 6：增量更新机制（禁止全量重写）

任何变更完成后，**禁止全量重写整个知识库**，必须按照"影响范围最小化"原则增量更新。

**三层同步更新矩阵**：

| 知识库文件 | 更新触发条件 | 更新方式 | 必须包含 |
|-----------|-----------|---------|---------|
| `PROJECT_KNOWLEDGE_BASE.md` (BASE) | 1. 新增模块<br>2. 架构重大调整<br>3. 技术栈变更 | 只更新版本号、变更记录索引、受影响的模块摘要 | ✅ 变更记录（倒序）<br>✅ 版本号递增 |
| `PROJECT_KNOWLEDGE_DETAIL-*.md` (DETAIL) | 1. 业务逻辑变更<br>2. 接口变更<br>3. 配置变更<br>4. 算法/流程变更 | 只修改受影响的模块域章节，其他保持不动 | ✅ 变更记录（倒序）<br>✅ 变更影响范围说明 |
| `docs/knowledge-base/*.puml` (流程图) | ⚠️ **只要代码流程变了就必须更新**<br>1. 状态机状态/跃迁变更<br>2. 调用链变更<br>3. 业务流程变更<br>4. 模块依赖关系变更<br>5. 协议报文格式变更 | ✅ **绝对禁止删掉重写**<br>只修改图中有变化的节点/箭头<br>不影响的部分保持原样 | ✅ 变更记录追加一行（倒序）<br>✅ 版本号和 BASE 同步 |

**强制执行标准**：
- 代码合并前必须先完成对应的知识库更新
- PUML 更新和代码更新必须在同一个 MR/PR 中提交
- 只要代码中流程逻辑变了，对应的 PUML 必须同步更新
- 设计文档中引用的 PUML 节点编号变更时必须同步更新
- 所有文件的版本号必须保持一致（BASE v2.3 → 所有 PUML 也是 v2.3）

---

### 规则 7：设计评审必须包含「知识库一致性检查」

设计评审的 checklist 必须增加：
- [ ] 设计是否引用了对应的知识库 PUML 流程图？
- [ ] 预计的知识库变更范围是否明确？
- [ ] 设计和已有实现是否存在冲突？
- [ ] 变更完成后谁负责更新知识库？

---

### 规则 6.1：测试报告完成后的知识库更新 SOP

测试报告确认通过后，**48 小时内必须完成对应的知识库增量更新**，按以下顺序执行：

**Step 1：更新 PUML 流程图（优先级最高）**
1. 根据本次变更的影响范围，找出需要更新的 .puml 文件
2. **只修改有变化的节点/箭头**，不影响的部分保持不动
3. 在文件头部「变更记录」中追加一行新记录（版本号与 BASE 同步）
4. 在线渲染验证无误后提交

**Step 2：更新 DETAIL 文档**
1. 只修改受影响模块域对应的章节
2. 在章节顶部追加「变更记录」说明
3. 同步更新接口、配置、数据结构等有变化的内容

**Step 3：更新 BASE 文档**
1. 版本号 + 1（如 v2.3 → v2.4）
2. 在「变更历史」章节追加本次变更记录
3. 更新受影响的模块摘要
4. 更新「PUML 流程图索引」表格中的版本信息

**Step 4：一致性校验**
- [ ] BASE、DETAIL、PUML 三者版本号完全一致
- [ ] 所有变更的 PUML 都追加了变更记录
- [ ] 代码中提到的流程编号和 PUML 中的节点可以对应
- [ ] 在线渲染所有更新的 PUML，确认无语法错误

## 常见问题

### Q1: 如果我随便开一个 Claude Code 会话就可以使用吗？

**A:** ❌ 不行。必须满足：

1. ✅ **工作目录正确**：必须 `cd` 到 `本仓库根目录（claude-code-cicd）` 这个目录，然后在这里启动 `claude`
2. ✅ **Git 仓库已初始化**：本目录已经是 Git 仓库了，所以只要 cd 对目录就行
3. ✅ **Claude Code 版本支持**：需要较新版本的 Claude Code CLI 支持自定义 Agent 和技能

为什么？因为所有的配置（`CLAUDE.md` 规则、`.claude/agents/` 里的 Agent 定义）都在这个目录里，换目录 Claude 就读不到这些配置，就不会按我们的流程工作。

---

### Q2: 我可以在其他项目使用这个流程吗？

**A:** 可以。设计上就是**共用框架 + 多项目分离产出**，支持同时处理多个项目。

**使用方式：**
1. 始终在 `本仓库根目录（claude-code-cicd）` 启动 Claude
2. 处理哪个项目，就提供那个项目的路径
3. 所有文档都输出到对应项目自己的目录下
4. 框架目录保持干净，不会和项目文件混在一起，避免冲突

---

### Q3: 是否必须从需求分析开始？可以直接从 PRD 开始吗？

**A:** 流程是按顺序设计的，但你可以跳步。如果你确认需求已经非常清晰，可以在一开始就说：
> "需求已经澄清，直接生成 PRD，跳过需求分析的待澄清环节"

AI 会直接生成 PRD。推荐按流程走一遍，需求分析阶段能帮你发现很多考虑不周的地方。

---

### Q4: 每个阶段都必须人工确认吗？可以全自动一次性跑完吗？

**A:** 本流程设计就是**每个阶段需要人工确认**，原因：
- AI 理解需求可能出错，早发现早修复成本更低
- 你对项目的需求和设计有控制权，可以随时调整方向

如果你对 AI 很有信心，可以说：
> "一次性生成需求分析、PRD、设计文档，然后我一起评审"

AI 会连续生成多个文档，然后一起给你评审。

---

### Q5: 如果评审发现问题怎么办？

**A:** 很简单，直接告诉 AI 哪里需要改，改什么：
> "PRD 里第三个功能需求不对，应该改成 xxx"

AI 会修改对应文档，修改完你再重新确认。

---

### Q6: 历史项目私域知识库一定要生成吗？

**A:**
- ✅ **需要做：** 在现有历史项目上开发新功能 → 帮 AI 理解现有代码
- ❌ **可以跳过：** 从全新空白开始新项目 → 不需要历史项目，直接跳过

---

### Q7: 这个流程和 Git 的关系是什么？每个任务都要提交吗？

**A:** 是的，每个任务完成后都会自动 Git 提交（提交在目标项目，不是框架目录）。好处：
- 每个阶段的产出都有版本记录
- 如果需要回滚，可以回到上一个阶段
- 你可以清楚看到每个阶段做了什么

---

### Q8: 如果我不想要某个阶段的产出，可以删掉重来吗？

**A:** 完全可以。Git 可以很方便地回滚：
```bash
# 在目标项目目录
cd 目标项目路径
git log                   # 查看提交历史
git reset --hard <commit-id>   # 回滚到指定提交
```
然后重新开始就行。

---

### Q9: 如果我忘了用 `/project-cicd-status`，是否每次都需要带目录？

**A:**
- ✅ **只要你第一次开始任务（任务2或任务3）时给了路径**，我就会记住，后续任务**不需要**每次都带
- ✅ `/project-cicd-status` 主要用于：
  1. 新开 Claude 会话后，恢复记忆告诉你当前在哪个项目
  2. 切换到另一个项目开发
  3. 忘记当前项目路径时，查看状态
- 如果你一直在同一个会话中处理同一个项目，完全不需要反复用这个命令

---

### Q10: 需求变了，要重新从头走一遍流程吗？

**A:** ❌ 不需要。使用任务9（需求变更），AI 会自动分析变更影响范围，只增量重做受影响的阶段。比如只是改个按钮文案，可能只需要更新 PRD 和代码，不需要重新做架构设计。

---

### Q11: 知识库每次都要全量重新生成吗？

**A:** ❌ 不需要。
- **首次**（任务2）是全量扫描，理解整个项目
- **后续更新**（任务8.5）都是增量，只更新本次变更涉及的章节
- 不管是正常需求实现还是需求变更，流程走完后都会自动执行知识库增量更新
- 知识库末尾有更新记录表，可以清楚看到每次更新了什么

---

### Q12: 任务9需求变更时，我需要判断变更大小吗？

**A:** ❌ 不需要。你只需要描述变更内容，AI 会自动分析影响范围并告诉你需要重做哪些阶段。你确认范围后 AI 才开始执行。

## 知识库贯穿整个开发流程（强制规则）

> 🎯 **核心理念：知识库 = 单一事实源（Single Source of Truth）**
> 所有开发阶段都必须「先读知识库，再写知识库」，不能脱离知识库单独进行

### 规则 1：PUML 流程图的变更记录机制
**所有 PUML 文件必须包含标准元数据头 + 变更记录注释**（模板如下，`{变量}` 部分根据实际项目替换）：

```plantuml
@startuml
' 项目：{项目名称，如：hw_swl_app}
' 流程图类型：{流程图类型，如：OTA升级流程 / 协议报文处理}
' 生成时间：{YYYY-MM-DD}
' 激活标签：{对应的特征标签，如：🔄 OTA/热更新}
'
' 变更记录（倒序排列，最新的在最上面）：
' v{版本号} - {日期} - {变更内容描述}
' v{版本号} - {日期} - {变更内容描述}
'
' ⚠️ 重要：使用最通用的 skinparam 语法，确保所有版本兼容
' 禁止使用 skinparam xxx { ... } 块语法！
' 禁止使用特定类型的 skinparam（如 rectangleBackgroundColor 等）
skinparam backgroundColor #FEFEFE
skinparam BackgroundColor #E8F4FD
skinparam BorderColor #2196F3
skinparam NoteBackgroundColor #FFF9C4
skinparam NoteBorderColor #FBC02D
skinparam ArrowColor #555555

' ⚠️ 语法规范（严格遵守）：
' - Activity 图用：start / :xxx; / if / split / stop
' - State 图用：[*] --> state / state "xxx\nyyy" as s1
' - 禁止混用两种语法（State 内不能用 :xxx;）

' {流程图内容...}

@enduml
```

**元数据头强制要求**：
- 不能缺失任何一行
- 版本号必须和知识库版本号一致
- 变更记录必须倒序排列（最新的在最上面）
- 样式配置必须和模板一致，保证所有流程图风格统一

---

### 规则 2：需求变更阶段必须参考知识库
- **读**：读取相关模块的 DETAIL 文档 + 对应的 PUML 流程图，评估变更影响范围
- **写**：变更完成后，**增量更新**受影响的知识库章节，并在变更记录中追加条目
- **禁止**：不看已有实现就凭空设计变更方案

---

### 规则 3：需求分析 / PRD 阶段必须建立知识库锚点
- **读**：读取 BASE.md 整体架构 + 技术栈约束，确保需求不超出已有技术能力
- **读**：参考同领域已有 PUML 流程图，复用已验证的实现模式
- **写**：在 PRD 中**必须增加「知识库锚点」章节**，标明：
  - 关联知识库版本
  - 关联的模块域
  - 关联的流程图文件
  - 预计会修改哪些知识库内容
- **写**：新增需求涉及新流程的，在 PRD 中附带 PUML 流程图草稿

---

### 规则 4：软件设计阶段强制引用 PUML 流程图（必须校验）
✅ **必须引用已有 PUML 流程图作为基准**，不能脱离已实现的代码架构  
✅ 修改流程的，必须在设计文档中标注「此设计修改了 `{文件名}.puml` 中第 X 节点」  
✅ 新增流程的，设计评审通过后必须生成新的 `*.puml` 文件并入知识库  

❌ **禁止**：设计和已实现代码完全脱节，出现"设计一套、实现另一套"  
❌ **禁止**：只写设计文档不更新知识库，导致设计和实现两张皮  

---

### 规则 5：所有开发文档必须包含「知识库锚点」
需求分析文档、PRD、设计文档、测试报告，**每个文档顶部必须包含**：
```markdown
## 知识库锚点
- 关联知识库版本：`PROJECT_KNOWLEDGE_BASE.md @ v2.1`
- 关联模块域：`加密模块域`、`升级模块域`
- 关联流程图：`ota_flow.puml`、`security_flow.puml`
- 预计变更：将修改 `ota_flow.puml` 第 3-5 节点，新增降级流程
```

---

### 规则 6：增量更新机制（禁止全量重写）
任何变更完成后，**禁止全量重写整个知识库**，必须增量更新：
- `BASE.md`：只更新版本号、变更记录索引、受影响的模块摘要，其他不动
- `DETAIL-*.md`：只更新受影响模块域的内容，其他模块保持不动
- `*.puml`：只修改有变更的流程图，其他保持原样
- 每个文件顶部必须有「变更记录」章节，按版本倒序排列

---

### 规则 7：设计评审必须包含「知识库一致性检查」
设计评审的 checklist 必须增加：
- [ ] 设计是否引用了对应的知识库 PUML 流程图？
- [ ] 预计的知识库变更范围是否明确？
- [ ] 设计和已有实现是否存在冲突？
- [ ] 变更完成后谁负责更新知识库？
