# 子代理委派规则（避免主会话上下文爆炸）

## 目标

明确 DevPilot 流水线中**哪些场景必须委派给子代理**、**委派给哪个子代理**、**如何写委派 prompt**，避免主会话上下文满了任务被停止。

## 核心原则

1. **主会话只做 3 件事**：preflight + 用户确认 + 接收子代理报告
2. **子代理独立运行**：主会话不读取子代理的中间结果
3. **子代理返回报告控制在 800 字以内**：只返回摘要，不返回完整文档
4. **子代理失败时（如配额超限）**：用 SendMessage 续接，不重派（保留上下文）
5. **长任务可后台运行**：`run_in_background=true`，主会话继续其他工作

| 阶段 | 任务 | 委派给 | 委派理由 |
|------|------|--------|---------|
| 任务2 | 知识库生成（全量） | `general-purpose` | 扫描 1000+ 文件 |
| 任务2 | 知识库生成（含 CodeGraph） | `general-purpose` | 读 .codegraph + 扫描 |
| 任务8.5 | 知识库增量更新 | `general-purpose` | 读 13-50 文件 + 现有知识库 + 设计文档 |
| 任务3 | 需求分析（M/L 级） | `requirements-analysis-agent` | 读知识库 + 项目背景 |
| 任务4 | PRD 生成（M/L 级） | `prd-generation-agent` | 读需求分析 + 知识库 |
| 任务5 | 软件设计（M/L 级） | `software-design-agent` | 读 PRD + 知识库 + 写设计 |
| 任务6 | 代码实现（M/L 级） | `code-implementation-agent` 或 `feature-implementation-agent` | 读设计 + 写代码 |
| 任务7 | 测试用例生成 | `testing-implementation-agent` | 读设计 + 已实现代码 |
| 任务8 | 测试报告 | `testing-implementation-agent` | 执行测试 + 收集结果 |
| 任务9 | 需求变更影响分析 | `change-request-agent` | 对比现有文档 |
| 调试 | 系统化调试 | `general-purpose`（带 systematic-debugging 指令） | 调试过程长 |
| 集成测试 | E2E / 浏览器测试 | `functional-testing-agent` | Playwright 操作日志大 |
| 大批量扫描 | >20 文件批量读取 | `Explore` 或 `general-purpose` | 扫描结果占用大 |
| 全库搜索 | 跨多目录 Grep | `Explore` | 搜索结果可能上百条 |

## 不该委派的场景（必须主会话做）

| 场景 | 理由 |
|------|------|
| 需求标识建议与确认 | 与用户交互 |
| S/M/L 分级评估与确认 | 与用户交互 |
| preflight 自检 | 需要用户确认是否用 CodeGraph |
| 阶段切换决策 | 流程门控，需主会话判断 |
| 阶段完成确认 | 与用户交互 |
| 简单问答、咨询 | 无需委派 |
| 单文件小修改（S 级） | 直接改即可 |

## 子代理选择决策树

```
任务是 DevPilot 流水线阶段？
├─ 是 → 用对应专业 agent（见上表）
└─ 否 →
   任务涉及大量文件读取/扫描？
   ├─ 是 →
   │  ├─ 是搜索/定位类 → Explore
   │  └─ 是执行/生成类 → general-purpose
   └─ 否 →
      任务涉及浏览器测试？
      ├─ 是 → functional-testing-agent
      └─ 否 → 主会话直接做
```

## 委派 prompt 模板

```markdown
你是 DevPilot 流水线的子代理，负责执行 [任务名]。

## 项目信息
- 目标项目根目录：[绝对路径]
- DevPilot 框架目录：[绝对路径]
- 本次任务：[描述]
- 变更级别：[S/M/L]

## 输入文件（已确定，无需自行查找）
- [文件1 绝对路径] —— [用途]
- [文件2 绝对路径] —— [用途]
- [文件3 绝对路径] —— [用途]

## 执行步骤
1. [Step 1: 具体操作]
2. [Step 2: 具体操作]
3. [Step 3: 具体操作]

## 返回报告（严格控制在 800 字以内）

返回以下摘要，**不要返回完整文档内容**：

1. **执行状态**：成功 / 部分完成 / 失败
2. **读取文件数**：约 N 个
3. **更新/生成文件列表**：
   - [文件路径] —— [更新了什么]
4. **关键变更点**（5-10 条要点）
5. **遇到的问题**（如有）
6. **上下文使用估算**：读了多少文件、写了多少内容（粗略字数）

## 约束
- 不要返回完整文档内容，只返回摘要
- 不要修改无关文件
- 不要在子代理中询问用户（无法交互）
- 遇到问题记录但继续，不要中断
- 若发现任务范围超出预期，记录并返回，由主会话决策
```

## 与 CodeGraph 的组合（最佳实践）

CodeGraph 提供**精准定位**，子代理提供**隔离执行**，两者互补：

```
主会话: codegraph fn-impact <函数> → 精确定位 N 个文件（+0.5KB）
主会话: 委派子代理，把 N 个文件路径列表传给它
  ↓
子代理: 读这 N 个文件 + 生成报告（爆也不影响主会话）
子代理: 返回报告（+0.5KB）
  ↓
主会话: 累计增加 1KB，继续下一步
```

**示例（intl-algorithm 知识库增量更新）**：

```
主会话: codegraph fn-impact JITSKF_encrypt_data
  → 输出：13 个文件受影响
主会话: 委派 general-purpose 子代理
  prompt 中明确：
  - 目标项目路径
  - 13 个文件路径列表（来自 codegraph 输出）
  - 现有知识库路径
  - intl-algorithm 设计文档路径
  - 增量更新规则（需求索引 + 模块描述 + 变更记录）
子代理: 独立完成读取 + 写入
子代理: 返回"✅ DETAIL 已更新，13 模块描述同步，变更记录追加"
主会话: 接收报告，继续下一步
```

## 失败处理

### 子代理失败常见原因

| 失败原因 | 表现 | 处理 |
|---------|------|------|
| API 配额超限 | 429 错误 | 等 2026-07-11 重置后用 SendMessage 续接 |
| 子代理上下文爆 | 子代理中途返回错误 | 拆分任务，派多个小子代理 |
| 文件路径错误 | 子代理找不到文件 | 主会话先验证路径，再委派 |
| 任务范围超预期 | 子代理返回"范围超出" | 主会话决策：拆分 / 升级 / 终止 |

### SendMessage 续接（保留上下文）

子代理失败后，主会话不要重新派一个新子代理（会丢失之前的上下文），用 SendMessage 续接：

```
SendMessage({
  to: "子代理 ID",
  message: "继续之前未完成的任务，从 Step X 开始..."
})
```

子代理会保留之前所有工具调用的上下文，从断点继续。

## DevPilot 各阶段应用示例

### 任务2 知识库生成（1702 文件大项目）

```
主会话:
  1. 执行 preflight-kb.ps1 → 输出项目规模（+0.5KB）
  2. 询问用户是否用 CodeGraph
  3. 用户确认后，委派子代理：
     - subagent_type: general-purpose
     - prompt 中包含：
       * 执行 preflight-kb.ps1 -Build（codegraph build）
       * 读 SKILL.md 了解流程
       * 扫描源码（用 .codegraph 加速）
       * 生成 PROJECT_KNOWLEDGE_BASE.md + DETAIL.md
       * 返回报告（800 字以内）
  4. 接收子代理报告（+0.5KB）
  5. 告诉用户：知识库已生成，路径 X
```

### 任务8.5 知识库增量更新

```
主会话:
  1. 回顾本次流程变更了哪些模块（已知，无需扫描）
  2. 委派子代理：
     - subagent_type: general-purpose
     - prompt 中包含：
       * 读现有 DETAIL
       * 读本次需求的设计文档
       * 增量更新 DETAIL（需求索引 + 模块描述 + 变更记录）
       * 返回报告
  3. 接收报告
  4. 告诉用户：DETAIL 已更新，版本 vX.Y
```

### 任务6 代码实现（M 级 TDD）

```
主会话:
  1. 确认设计文档已通过评审
  2. 委派子代理：
     - subagent_type: code-implementation-agent
     - prompt 中包含：
       * 设计文档路径
       * 知识库路径（指导编码风格）
       * 测试代码目录（需用户确认）
       * TDD 要求（RED/GREEN/REFACTOR）
       * 返回报告（测试结果 + 代码位置）
  3. 接收报告
  4. 告诉用户：代码已生成，测试通过
```

## 自检清单（每次委派前）

主会话在调用 Task 工具前，自检：

- [ ] 任务是否属于"必须委派"场景？
- [ ] 子代理类型选择是否正确？
- [ ] prompt 是否包含所有必要文件路径（绝对路径）？
- [ ] prompt 是否明确返回报告格式（800 字以内）？
- [ ] prompt 是否说明约束（不修改无关文件、不询问用户）？
- [ ] 是否需要先执行 codegraph fn-impact 精确定位？
- [ ] 长任务是否考虑 run_in_background=true？

## 自检清单（每次委派后）

主会话接收子代理报告后，自检：

- [ ] 报告是否在 800 字以内？
- [ ] 报告是否包含执行状态、文件列表、关键变更点？
- [ ] 是否有未解决的问题需要主会话决策？
- [ ] 是否需要继续下一步（委派下一个子代理）？

## 与 DevPilot 框架的集成建议

当前 DevPilot 框架的 CLAUDE.md 已规定各阶段"委派 Agent"，但**没有强制要求主会话不读取中间结果**。建议在 CLAUDE.md 中增加：

```markdown
## 子代理委派强制规则

DevPilot 各阶段委派 Agent 时，主会话 MUST：
1. 不读取子代理的中间工具调用结果
2. 只接收子代理最终报告（控制在 800 字以内）
3. 子代理失败时用 SendMessage 续接，不重派

违反此规则会导致主会话上下文爆炸，任务被停止。
```

## 测试与反馈

按本规则执行后，观察：

- [ ] 主会话上下文是否始终在安全水位（<30% 使用率）
- [ ] 是否能连续处理多个长任务不爆
- [ ] 子代理报告是否准确（无遗漏）
- [ ] 失败时是否能用 SendMessage 续接

反馈后可调整：
- 必须委派的场景清单
- 子代理类型映射
- prompt 模板
- 返回报告字数上限
