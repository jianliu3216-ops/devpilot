# jit-context-compress — 阶段间上下文压缩

> 阶段推进时，用 `docs/{需求}/.handoff/{目标阶段}.context.md` 代替全量前序文档带进上下文，省 25-30% token。

## 触发

```
/jit-context-compress <目标项目路径> <需求标识> <目标阶段>
```

自然语言：`上下文压缩` / `压缩上下文` / `生成 handoff 压缩包`

目标阶段 ∈ {`prd`, `design`, `build`, `test`, `report`, `kb`}

## 做什么

1. 扫描 `docs/{需求标识}/` 下目标阶段**之前**的已完成文档（00-原始需求 → 05-测试报告）
2. 对每份生成压缩条目：文件路径、SHA256、行数、`##` 章节标题列表、每章首句要点
3. 输出 `docs/{需求标识}/.handoff/{目标阶段}.context.md`，末尾附「按需下钻建议」（需要细节时读哪个文件哪一行）
4. 旧压缩包存在且源文档哈希未变 → **复用旧包**，不重复生成

## 执行（MUST 用工具跑）

```bash
node "$FRAMEWORK/skills/jit-context-compress/scripts/compress-handoff.js" "<目标项目绝对路径>" "<需求标识>" "<目标阶段>"
```

Windows PowerShell 同样调用 `node`，路径用绝对路径。`$FRAMEWORK` 来自 `~/.claude/devpilot-framework-path`。

## 流水线硬规则（阶段推进时 MUST 执行）

1. **进入新阶段前**：运行本脚本生成该阶段的 `.context.md`（带上目标阶段名）
2. **只读压缩包**：恢复前序上下文只读 `.handoff/{阶段}.context.md`，**不全文复读前序文档**
3. **按需下钻**：需要具体细节时，按压缩包「按需下钻建议」读原文档对应章节/行
4. **文档被改后**：重跑脚本，哈希变化会自动重新生成压缩包
5. 产出写在**目标项目** `docs/{需求标识}/.handoff/`，禁止写框架目录

## 压缩包格式示例

```markdown
# 阶段 handoff 上下文包（user-login → build）
> 生成时间：2026-08-19 14:30 · fingerprint: a1b2c3d4…
> 使用规则：只读本压缩包恢复上下文，按需下钻，不全文复读。

## 前序文档清单
- **需求分析** — `01-requirements-analysis.md` (sha256: 3f9a…) · 132 行
  - 章节: 项目背景 / 目标 / 功能需求(12条) / 非功能需求 / 待澄清
  - 「功能需求」要点: 用户登录需要支持用户名密码登录；支持短信验证码登录…
- **PRD** — `02-prd.md` (sha256: c0de…) · 90 行
  - …

## 按需下钻建议
- 需要「功能需求」细节 → 读 `01-requirements-analysis.md` 第 24 行附近
```

## 常用阶段映射

| 目标阶段 | 纳入前序文档 |
|---------|-------------|
| prd | 00, 01 |
| design | 00, 01, 02(+02a) |
| build | 00, 01, 02, 03(+02a/03a) |
| test | 00, 01, 02, 03, 04(+02a/03a/04a) |
| report | 00 ~ 05 全部 |
| kb | 00 ~ 05 全部 |

## 牢记规则

- 压缩包是**机器生成的镜像**，文档仍是人可读的事实源；两者由哈希指纹保证一致
- 禁止手改 `.handoff/*.context.md`（下次运行会被哈希校验覆盖或复用）
- 源文档哈希未变时脚本会自动复用旧包，重复运行零成本
