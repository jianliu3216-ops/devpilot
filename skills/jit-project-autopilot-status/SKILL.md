# Autopilot 智能流水线 - 状态

**作用：** 新开会话后一键恢复工作状态。如果当前会话 Autopilot 尚未激活，自动加载规则并确认目标项目，无需先执行 init。

## 执行步骤：

### 步骤 0：自动激活检测（新增 — 解决"每次都要先 init"的痛点）

1. **定位框架路径**：读取 `~/.claude/devpilot-framework-path` 获取框架目录（记为 `$FRAMEWORK`），读取 `$FRAMEWORK/VERSION` 获取版本号
2. **加载行为规则**：按顺序读取：
   - `$FRAMEWORK/CLAUDE.md` — 流程门控、禁止行为、优先级声明
   - `$FRAMEWORK/.claude-collective/cicd-rules.md` — 触发关键字、分级规则、输出路径
3. **输出激活确认**：读取完成后输出 `🚀 Autopilot v{版本号} 已激活`
4. **检测目标项目路径**：
   - 如果当前会话已指定目标项目 → 直接进入步骤 1
   - 如果当前工作目录**不是**框架目录 → 自动识别为候选项目路径，提示确认："检测到当前目录为 `<路径>`，是否作为目标项目？"
   - 以上都不满足 → 询问用户："请提供目标项目路径"
5. **确认后记住路径**，本会话后续所有操作自动使用

### 步骤 1：扫描项目状态

4. **扫描目标项目** `docs/` 目录，按下方「状态检查规则」完整执行，禁止凭文件数量猜测：
   - 框架目录：共用框架环境已就绪
   - 目标项目：列出每个需求的状态，**必须标注变更级别**
   - **强制顺序**：对每个需求目录，先读 CHANGELOG.md 取状态 → 再读 `head -30 docs/{id}/01-requirements-analysis.md` 取级别 → 按级别判定文档完整性

### 步骤 2：输出状态 + 下一步建议

5. **总结当前状态**（格式见下方「状态输出格式」）
6. **提示用户输入下一步**：给出自然语言触发示例

## 需求标识规则（多需求区分）

每个需求必须有一个**英文短标识**（kebab-case），用于创建独立的文档目录。

### 新需求启动流程：

1. 用户输入需求描述（中文即可）
2. AI 自动生成英文标识建议
3. **必须提示用户确认**：
   ```
   需求【用户登录注册模块】英文标识建议：user-login
   是否需要调整？（确认后将以 docs/user-login/ 作为文档目录）
   ```
4. 用户确认或调整后，以该标识创建目录

### 目标项目目录结构（按需求隔离）：

```
目标项目/
├── docs/
│   ├── knowledge-base/                    # 共享，整个项目一份，增量更新
│   │   └── PROJECT_KNOWLEDGE_BASE.md
│   │
│   ├── user-login/                        # 需求A：全部阶段文档在一起
│   │   ├── 00-原始需求.md                 # 永久记录，先于01创建
│   │   ├── 01-requirements-analysis.md
│   │   ├── 02-prd.md
│   │   ├── 03-software-design.md
│   │   ├── 04-test-cases.md
│   │   ├── 05-test-report.md
│   │   └── CHANGELOG.md                  # 该需求的变更记录
│   │
│   └── message-push/                      # 需求B：全部阶段文档在一起
│       ├── 00-原始需求.md                 # 永久记录，先于01创建

│       ├── 04-test-cases.md

```

### 用户输入格式：

```

```

## 状态检查规则（支持需求变更识别）

扫描目标项目 `docs/` 目录时，按以下逻辑判断每个需求的状态。

### ⚠️ 强制步骤（必须先于状态判定执行）

**在判断每个需求的文档完整性之前，必须先读取 `01-requirements-analysis.md` 获取变更级别。**
不允许仅凭文件名数量判断"缺失文档"。

```
for each 需求目录:
  1. 先读 CHANGELOG.md          # 取真实状态（暂停/变更中），这是唯一权威来源
  2. head -30 docs/{id}/01-requirements-analysis.md   # 获取级别
  3. 检查 00-原始需求.md 是否存在  # 所有级别强制要求，需求标识确认后立即创建
  4. 根据级别+CHANGELOG 状态综合判断文档完整性（见下表）
```

### 按级别判断文档完整性

| 级别 | 必需文档 | 判断条件 |
|------|---------|----------|
| **所有级别** | 00 | `00-原始需求.md` — 需求标识确认后立即创建，先于 01 |
| **S级** | 00 + 01 + 05 | 中间阶段（02/03/04）全部跳过 |
| **M级** | 00 + 01 + 02 + 03 + 04 + 05 | 全阶段文档 |
| **L级** | 00 + 01 + 02 + change-strategy + 04 + 05 | PRD后走变更策略而非software-design |

**S 级缺 02/03/04 是正常的，不应标记为"进行中"。但 00 是所有级别强制要求的，缺失即为不完整。**

### 状态定义：

| 状态 | 含义 | 判断条件 |
|------|------|----------|
| ⏳ 待开始 | 需求目录已创建但无文档 | 目录存在，内部无阶段文档 |
| 🔄 进行中 | 某个阶段正在执行 | 按级别判断，必需文档不全 |
| ✅ 已完成 | 按级别的必需文档齐全 | 参照上表 |
| ⏸️ 暂停 | 产品决定暂缓 | CHANGELOG.md 或 01 文档明确标注"暂停" |
| 🔁 变更中 | 需求变更流程正在执行 | CHANGELOG.md 中有未关闭的变更记录 |
| ✅✅ 变更完成 | 变更流程已走完 | CHANGELOG.md 中最新变更记录状态为"已完成" |

### 变更场景状态检测：

检查每个需求目录下的 `CHANGELOG.md`，如果存在则解析变更记录：

```
## 变更记录

### 变更1：增加 OAuth 第三方登录
- 状态：🔄 变更中          ← 检测到"变更中"，该需求状态显示 🔁 变更中
- 日期：2026-04-28
- 影响阶段：02-prd, 03-software-design
- 已重做：02-prd ✅
- 待重做：03-software-design ⏳

### 变更2：增加验证码功能
- 状态：✅ 已完成          ← 已关闭，不影响当前状态
- 日期：2026-04-25
- ...
```

### 状态输出格式：

```
📊 项目状态总览

项目路径：D:\projects\my-app

需求列表：
  ✅ user-login（用户登录注册） [S级]   — 01+05，S级中间阶段全部跳过
       最后变更：2026-04-25 验证码功能（已完成）
  🔁 message-push（消息推送） [M级]    — 变更中
       当前变更：增加邮件通知，影响 02-prd/03-software-design
       已重做：02-prd ✅
       待重做：03-software-design ⏳
  ⏸️ ipv6-support（IPv6支持） [L级]   — 产品决定暂停
  ⏳ order-export（订单导出）     — 待开始

知识库：✅ 已生成（2026-04-20）

下一步建议：
  - message-push：继续重做 03-software-design
  - order-export：输入"需求分析：订单导出功能"开始
```

## 牢记规则：

- 所有生成的文档和代码都必须**输出到目标项目目录**，不能输出到当前框架目录
- 每个需求的文档输出到 `docs/{需求标识}/` 目录下，不同需求完全隔离
- knowledge-base 保持共享（整个项目一份），变更时增量更新
- 每次调用 `/van` 时，必须拼上所有依赖文件的**完整绝对路径**
- 如果任务 2（私域知识库）已完成，必须在调用命令中添加指令：
  ```
  请参考 PROJECT_KNOWLEDGE_BASE.md 理解项目，不需要读取整个项目代码
  ```
- 每个阶段完成后，必须停下来等待用户确认，不能自动进入下一阶段
- 严格遵循顺序：任务 1 → 任务 2 → 任务 3 → 任务 4 → 任务 5 → 任务 6 → 任务 7 → 任务 8 → 任务8.5（知识库增量更新）
- **不管哪种场景**，只要流程走到最后一步（测试报告完成），**必须**执行知识库增量更新（任务8.5）
- 知识库增量更新：只更新本次变更涉及的章节，不需要全量重扫，追加更新记录
- 需求变更时使用任务9，AI自动分析影响范围，增量重做，不需要从头走全量流程

## 支持的场景：

### 场景1：正常需求实现
- 需求分析 → PRD → 软件设计 → 代码实现 → 测试用例 → 测试报告 → 知识库增量更新
- 用户输入示例：
  ```
  需求分析：我要做用户登录注册模块，目标项目：D:\projects\my-app
  ```
  AI 自动提示：
  ```
  需求【用户登录注册模块】英文标识建议：user-login
  是否需要调整？（确认后将以 docs/user-login/ 作为文档目录）
  ```

### 场景2：需求变更
- 描述变更 → AI影响分析 → 确认范围 → 增量重做 → ... → 测试报告 → 知识库增量更新
- 用户输入示例：
  ```
  需求变更：user-login 增加忘记密码链接
  ```
  ```
  需求变更：message-push 新增邮件通知支持
  ```

## 输出要求：

### 情况 1：目标项目路径未确定（自动激活中）
- 自动检测当前目录，提示用户确认
- 用户确认后输出简要激活确认 + 项目状态总览

### 情况 2：目标项目路径已确定
- 输出框架版本 + 目标项目路径
- 汇总当前目标项目各需求状态（包含变更中状态识别）
- 格式见上方"状态输出格式"
- **额外检查**：如果所有需求所有阶段已完成，检查知识库是否有更新记录
- 提示用户输入开始下一阶段任务，给出输入格式示例
- 如果项目已完成所有阶段，提示用户可以进行需求变更
